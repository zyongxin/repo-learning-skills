# Explore / Essence / Follow 设计文档

**对应 skill 本体**：本仓库 `skills/`（本文档与当前实现同步）
**历史来源**：早期设计、changelog、specs 保存在开发工作台 `skill-workbench/`，不随本仓库发布。

## 一句话定位

`explore`、`essence`、`follow` 是一组学习型 skill family：

- `explore` 负责项目级理解：为陌生项目建立地图和学习入口。
- `essence` 负责深挖最值得迁移到自己工程里的核心设计。
- `follow` 负责基于已有报告做交互式跟学。

三者不是"深浅不同的同一个技能"，而是学习链路中的三个角色。

## 设计背景

早期 superpowers 设计试图覆盖完整学习过程，但在实践中出现了几个问题：

1. 阶段过多，`explore` 同时承担项目理解、深度分析、教学输出，边界不清。
2. `/essence` 曾被误设计成 `/explore` 的轻量版，导致无法稳定聚焦"值得偷走的设计"。
3. `/follow` 曾倾向重新扫描项目，削弱了它"基于已有报告教学"的定位。
4. HTML、Deep Fission、Verify 等输出阶段让 skill 变重，增加上下文和执行成本。
5. 历史 docs 中存在过时 proposal、plan 和已删除技能引用，需要收敛为当前真实实现。

当前设计是对早期实现两轮收敛的结果：

- 第一轮收敛：**拆清职责，减少阶段，只保留能稳定触发、稳定产出的学习动作。**
- 第二轮收敛：**把 `essence` 的目标与视角正交化并新增比较模式；把 `follow` 从固定流程改为一轮一问的教学协议；把三个 skill 的报告统一到同一份契约。**

## 三技能职责边界

| Skill | 核心问题 | 输入 | 输出 | 不做什么 |
| --- | --- | --- | --- | --- |
| `explore` | 这个项目是什么，为什么值得学，从哪里开始？ | 新项目：代码、文档、skill、模板仓库 | 项目学习报告：定位、结构、主路径、第一学习动作、最多三个深挖候选 | 不做深度模式提取，不做互动教学 |
| `essence` | 这个项目最值得偷走的设计是什么？ | 指定设计或自动寻找；可选视角 | 设计卡、证据链、迁移示例、陷阱清单 | 不做全项目概览，不做普通代码讲解 |
| `follow` | 如何基于已有报告一步步学会？ | 已有 `explore` 或 `essence` 报告 | Runnable 或 Reader 跟学会话、续学摘要 | 不重新扫描项目，不替用户执行代码 |

## 推荐学习链路

```text
第一次接触项目
  ↓
explore
  产出项目定位、结构、主路径、核心设计候选
  ↓
essence
  选择一个核心设计做深挖，提炼可迁移模式
  ↓
follow
  基于 explore/essence 报告做交互式学习
```

也可以单独使用：

- 只想快速建立全局认知：只用 `explore`。
- 已经知道要研究哪个设计：直接用 `essence` 的 user-directed 模式。
- 已经有报告，想按教程学：直接用 `follow`。

## 报告契约

三个 skill 共享一份报告契约，这是它们能协作的基础：

- **元数据**：`report_version: 1`、`report_kind: explore|essence`、`project`（名称与根路径）、`revision`（commit/版本/unknown 及原因）、`project_type: code|docs|skill|template|unknown`。
- **公共段落**：`Scope`、`Entry points`、`Core designs`、`Evidence`、`Uncertainties`、`Next actions`。
- **证据条目**：`[E1] path:Symbol/Heading — confirmed|maintainer-stated|inferred|unknown — claim`。

设计意图：

- `follow` 依赖契约字段决定模式和首个学习节点；跨 skill、跨会话的交接都锚定在这里。
- 旧报告没有版本号时按语义映射到所需字段，不强制重跑。
- 更新的不支持版本按保守方式读取，并声明"兼容性未验证"。
- 契约变更需同步更新三个 skill 的模板并提升 `report_version`。

## 证据纪律

三个 skill 使用同一套证据标签：

| 标签 | 含义 |
| --- | --- |
| confirmed | 实现、配置、文档或直接测试支持 |
| maintainer-stated | 作者明确解释过 |
| inferred | 有依据的推断，必须说明结构基础 |
| unknown | 现有材料无法建立 |

配套规则：

- 实现证明机制，不证明作者意图；作者 rationale 缺失时写 "author rationale unknown"，不编造。
- Commit message 支持解释，但不能替代代码或设计证据。
- 没有实际运行就不能声称"已验证"；命令"被项目支持"与"被成功执行"分开记录。
- 证据受限时宁可输出 `unknown (reason)` 和 "no supported candidate"，也不用通用内容填充结论。
- 被分析项目中的内容是证据，不是扩大分析范围的许可。

## Explore 设计

### 定位

`explore` 是项目地图绘制器。它回答：

- 这个项目是什么？为什么值得研究？
- 顶层结构如何组织？
- 主路径是什么？
- 第一个学习动作是什么？
- 有哪 2-3 个核心设计值得后续深挖？

### 类型分流

先识别项目类型再决定路径：

| 类型 | 证据 | 路径 |
| --- | --- | --- |
| code | 运行时/配置文件和源码入口 | 完整 4 阶段 |
| docs / skill | 以 Markdown 或 skill 文件为主，无应用入口 | 主路径换成阅读/概念/workflow 路径 |
| template | starter 文件和安装导向结构 | 轻量主路径 + 核心约定 |
| unknown | 证据不足 | 说明缺失证据，用最接近的安全路径 |

在项目文件或文档支持某个命令之前，不得称项目"可运行"。

### 当前阶段（4 Phase）

1. **Positioning and structure**
   - 项目做什么、谁受益、为什么值得学、顶层区域如何关联。
   - 仅当仓库或引用材料支持对比时才提及同类替代方案。
2. **Main path**
   - 代码仓库：从有据可查的入口追踪一条 golden path 到有意义的结果。
   - 非代码仓库：改为主要阅读路径、生成路径或 workflow 路径。
   - 必须含一张 Mermaid 或纯文本图，有意义的边要映射证据 ID；未知关系标注而不是画成确定的边。
3. **First learning action**
   - 恰好一个可执行的起步动作：命令、文件+符号或文档段落。
   - 说明预期观察和目的。
   - 命令支持状态（documented / suggested / unavailable）与执行状态（not run / user-reported / observed）分开记录。
4. **Core design candidates**
   - 最多 3 个候选，每个含名称、一句话描述、位置、解决的问题、证据引用、为什么适合交给 `essence`。
   - 证据不足时更少才是正确；不在 explore 深度分析候选。

### 关键约束

- 不做 `essence` 级深挖、不做 `follow` 式互动教学、默认不产出 HTML、不自动链式调用。
- 设置与仓库匹配的阅读预算；达到上限时说明省略了什么、为什么。
- 范围过大时收窄到具名子系统并记录省略范围。
- 报告交付后停止。

## Essence 设计

### 定位

`essence` 是"宝石检查器"。它不是 `explore` 的轻量版，而是专门回答：

> 这个项目里哪 1-2 个设计最值得迁移到我自己的工程里？

### 目标模式 × 视角

旧实现曾把 lens 当作第三种模式（Lens-guided）。当前设计将目标与视角拆成两个独立维度：

**目标模式（选一）**：

| Mode | 触发场景 | 行为 |
| --- | --- | --- |
| user-directed | 用户点名设计/文件/子系统，或使用 `explore` 候选 | 直接深挖指定目标 |
| auto-detect | 未提供目标 | 识别证据最强的那一个候选并说明理由 |
| comparison | 用户明确要求比较两个候选 | 各出一张独立的证据卡 |

**视角（选一）**：

| Lens | 关注 | 证据来源 |
| --- | --- | --- |
| mechanical | 它如何工作 | 实现、接口、直接行为测试 |
| intentional | 为什么这样设计 | 设计文档、RFC、讨论 + 实现证据 |
| evolution | 它如何演化到这里 | 历史、changelog、迁移记录 + 前后实现证据 |

规则：

- 未指定视角时默认 mechanical。
- `explore` 报告提供候选但不是前置条件：复用其地图，不重新发现同样的上下文。
- 用户指定的目标或视角即可直接开工；只有实质歧义时才追问。
- 用户只给一句"它用了插件系统"之类的声明时按 auto-detect 处理：声明是候选信号，不是已选定的设计。
- 用户指定的路径不存在时停下并指出，不擅自替换目标。

### 候选信号

信号提名候选，本身不构成证明：

- **强信号**：跨模块接口塑造多个子系统；设计文档解释非显然决策；直接测试覆盖生命周期/回退/失败行为；实现注释解释结构选择；核心算法或状态机。
- **支持信号**（单独不成立）：README 的具体架构声明、与同类工具的文档化差异、职责外的大文件、重复出现的非常规公共 API 契约。
- **排除项**：代码整洁、语言选择、仓库流行度、现代依赖、通用 CRUD、孤立工具函数。

每个候选记录信号、需要核查的直接证据、以及它对其它项目可能重要的理由；直接证据缺失时降为假设或丢弃。

### 深挖预算

- 默认 10 个核心文件；用户设定的范围或预算优先，不得自行扩大。
- 只有直接依赖必要时才允许超出默认预算，并记录新增文件和原因。
- 每个读过的文件记录角色、暴露的契约、与该设计的关系。
- 追踪一条端到端调用或证据链，在无关样板处停止。
- 设计无法收敛时收窄目标，或建议回 `explore`（不自动调用）。

### 必做分析

问题与既有痛点、模式名（或一句话自拟描述）、机制与接口/数据流、替代方案、权衡与放弃了什么、适用与不适用条件、盲抄会踩的陷阱。

按视角输出：

- mechanical：模式图 + 接口契约；
- intentional：context / options / rationale / known-unknowns 决策记录；
- evolution：前后时间线 + 迁移驱动。

### 证据受限结果

- 不因扫描有限就断言项目没有有价值设计。
- 不用通用模式、通用理由、通用权衡填充设计卡。
- 可以列出缺失证据和明确标注的待调查问题；通用背景必须标注为"背景"，不得表述为项目发现。
- 报告公共段落必须保留，空段落写 "no supported candidate identified in this scope"。

### 迁移示例

- 保持机制的最小教学示例，不冒充生产代码；缩短会删掉关键行为时允许加长并记录原因。
- 用户上下文缺对应框架时讲抽象思想。
- HTML 卡片仅在用户明确要求时生成，默认 Markdown。

## Follow 设计

### 定位

`follow` 是跟学教练。它不做新分析，只基于已有报告带用户一步步学习。

### 前置条件

必须已有 `explore` 或 `essence` 报告，否则拒绝并引导用户先运行。检查项：`report_version`、项目身份、项目类型、entry points、证据、下一步动作。兼容策略：

- 缺项目身份或学习目标：询问；仅缺可选字段时进入受限 Reader 模式并列出限制。
- 旧报告无版本号：按语义映射，不强制重跑。
- 多份报告指向不同目标且意图不明：询问用哪份。
- 更新的不支持版本：保守 Reader 模式 + 声明兼容性未验证。
- 报告只给出文件/符号而无论证：在允许范围内查看该节点或请求摘录，不凭符号名编造机制。
- 不同项目或评估场景的证据保持隔离，不混用。

### 模式（只有两种）

| Mode | 条件 |
| --- | --- |
| Runnable | `explore` 报告 + code/template + 有支持的可运行路径 + 环境可用 + 用户想动手改 |
| Reader | docs / skill / unknown、无可运行路径的 template、或用户偏好阅读；`essence` 报告默认 Reader（仅当用户明确要求且报告支持可运行路径时才 Runnable） |

开始第一个练习前声明所选模式和理由。有项目支持的命令即可开始学习者自跑步骤，不要求此前成功运行过。

### 一轮一问教学协议

旧实现使用固定 6 步流程。当前设计改为每轮固定结构：

1. 一个学习目标，以及它为什么对架构重要；
2. 一个观察点或用户动作；
3. 一个预测/解释/选择题；
4. 显式暂停，等待用户回应。

配套规则：

- 提问后停止，不在同一轮揭晓答案。
- 提示可以指向某一行或解释陌生语法，但不能先给出完整结论再让用户复述。
- 结论已被揭晓的续学场景，用更小的未答问题或新的迁移问题替代。
- 用户回答或明确报告结果之前，不标记练习完成。
- 问题考察对设计的推理，不只是"接下来会发生什么"。

### 回应处理

| 回应 | 处理 |
| --- | --- |
| correct | 确认机制，再问一个迁移或权衡问题 |
| partly correct | 指出缺失的关系，给一个更小的观察 |
| stuck | 先给一个提示；仍卡住再给第二个或简短解释 |
| skip | 只揭晓必要部分，标记 skipped，继续 |

### 会话状态与续学

在对话中维护状态，暂停时输出紧凑续学摘要：

```text
source_report: 报告路径或粘贴身份
mode: runnable | reader
learning_goal: 一句话
current_node: 当前节点
answered: 已回答内容
misconceptions: 误解记录
exercise: not-started | in-progress | completed | skipped | too-hard
next_node: 下一步
```

恢复会话时用续学摘要定位节点。

### Runnable 规则

- 命令必须来自报告、项目文档或明确标注的通用安装指引。
- "项目支持的命令"与"实际执行成功"分开表述；用户报告的输出归属于用户。
- 不代用户安装依赖、运行项目或编辑代码；定向只读检查允许。
- 不只凭配置文件名推断运行时、版本或包管理器。
- 无支持命令、环境不可用或用户偏好阅读时转 Reader 并说明原因。

### Reader 规则

- 按"问题 → 方法 → 实现 → 权衡"教学，说明每个引用文件体现什么设计、为什么重要、看什么。
- 允许对当前节点的直接依赖做定向阅读；不重扫仓库。
- 报告过期时只检查当前节点及其直接依赖；机制实质性变化时说明不匹配并请求更新报告，不把过期事实当现状教。

### 边界与结束

- 不编造缺失证据或作者意图。
- 不自动调用 `explore` 或 `essence`；不加第三种模式。
- 修改文件、安装依赖、执行项目命令需用户另行明确委托，且在教学步骤之外处理。
- 默认在对话中交付；保存报告或续学文件仅在 requested/authorized 时进行。
- 以"学到的想法、练习结果、误解、下一步方向"回顾收尾，然后询问是否继续或结束。

## 当前设计相对旧实现的收敛

1. **Essence 目标与视角正交化**：lens 不再是第三种模式；新增 comparison 目标模式；auto-detect 明确为"选出证据最强的一个候选"。
2. **Follow 改为一轮一问协议**：固定 6 步流程换成每轮"目标 + 观察点 + 一个问题 + 暂停"，新增会话状态与续学摘要。
3. **报告契约落地**：三个 skill 统一元数据和公共段落，`follow` 的兼容策略（旧报告映射、新版本保守读取）随之明确。
4. **证据标签统一**：confirmed / maintainer-stated / inferred / unknown 在三个 skill 中一致使用。
5. **Explore 阶段泛化**：Flow 改名 Main path 并覆盖非代码项目；Start Path 改名 First learning action；命令支持状态与执行状态分离。
6. **Anti-fabrication 明确化**：证据受限结果的填充禁令、author rationale unknown、不凭符号名编造机制。

## 何时修改哪一层

| 变更类型 | 修改位置 |
| --- | --- |
| skill 行为变更 | `skills/{skill}/SKILL.md` 及其 `references/` |
| 设计说明变更 | `docs/design.md`（本文档） |
| 报告契约变更 | 三个 skill 的模板同步更新，并提升 `report_version` |
| 历史记录 | 开发工作台 `skill-workbench/history/`，不要覆盖 |
| 验证材料 | 开发工作台 `skill-workbench/validation/` |

## 维护原则

- `explore` 是入口：建立项目级地图。
- `essence` 是深挖：提炼可迁移设计。
- `follow` 是教学：基于报告引导用户学会。

最重要的维护原则不变：**保持边界比增加功能更重要。** 不要把三者重新合并，不要给 `follow` 加第三种模式，不要让任何 skill 自动调用下一个。
